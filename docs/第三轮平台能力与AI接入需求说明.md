> 文档状态：已确认，进入分阶段实施
> 版本：V1.0 确认版
> 日期：2026-09-20
> 适用项目：智学双擎本地 Node Web Service 版
> 确认依据：项目负责人于 2026-09-20 指示按本需求修改项目并上传 Git。
> 实施约束：按 P0→P3 分阶段交付；任何未落库、未通过引用校验或未形成运行记录的结果不得标注成功或 AI 生成。

## 1. 背景与目标

中国大学 MOOC 已形成课程建设、章节内容、测验、作业、考试、讨论、评分和课程数据统计的完整链路；学习通、雨课堂等平台强调移动教学、签到、随机选人、抢答、课堂测验、教学日志和 AI 备课。智学双擎不应复制一个庞大的通用教学平台，而应补齐支撑真实教学闭环所必需的基础能力，并强化自身“学生级学情诊断与个性化干预”的定位。

本轮目标：

1. 补齐课程内容、学习任务、轻量评价、通知和过程记录等基础能力。
2. 将班级统计、学生画像、智能问答和个人计划统一到同一套可信数据底座。
3. 增加可替换的大模型 API 接入层，支持国内可访问或学校私有部署的模型。
4. 建立原始区、暂存区、隔离区、可信区和服务区，防止演示数据、错误导入、模型输出或跨课程数据污染正式统计。
5. 所有“生成、保存、发布、完成”状态必须由服务端真实落库后返回，不允许前端假装成功。
6. 形成一项能够与主流平台拉开差异的核心能力：可验证的个体学习处方引擎。

## 2. 产品定位与实施边界

### 2.1 产品定位

智学双擎定位为：

> 可接入现有教务/学习平台、支持本地部署的学生学情诊断与个性化干预引擎。

平台重点完成“读取真实教学数据 → 形成可解释画像 → 回答课程问题 → 自动形成个人计划 → 跟踪执行效果 → 调整下一轮干预”，而不是在本轮重做大型视频平台、支付、证书或重型直播系统。

### 2.2 唯一核心差异化功能

本轮将“**可验证的个体学习处方引擎**”作为优先于通用平台功能的核心能力。这里的“优于”限定在“从学生诊断到干预效果验证的深度”这一维度，不宣称在课程资源数量、直播、题库规模或用户规模上整体超过学习通、MOOC 等平台。

主流平台通常能够展示学习进度、成绩、参与度和风险，但本功能必须继续向前完成：

```text
可信数据快照
  → 诊断到具体知识点和行为原因
  → 为每名学生生成不同的学习处方
  → 解释为什么推荐、预计改善什么
  → 学生按任务执行并留下完成证据
  → 使用同口径数据进行前后测量
  → 判断本轮干预是否有效
  → 自动调整下一轮处方
```

它不是一个“AI 建议文本框”，而是一条可追溯、可执行、可测量、可调整的服务端业务链路。比赛或产品介绍中的核心表达为：

> 其他平台主要告诉教师“学生发生了什么”，智学双擎进一步告诉教师“下一步具体做什么”，并验证“做完以后是否真的改善”。

### 2.3 本轮包含

- 课程与章节资源管理的最小闭环。
- 作业、练习、个人任务和完成证据。
- 公告、待办和站内通知。
- 班级/学生过程数据、统计口径和数据来源展示。
- 课程智能问答、教师 AI 助手、个性化计划、风险解释。
- 模型 Provider、模型网关、知识库和 AI 运行记录。
- 数据接入、质量校验、隔离、版本、回滚和审计。

### 2.4 本轮不包含

- 自研音视频转码、CDN、万人直播和在线支付。
- 国家级课程商城、证书、防作弊监考等重型平台能力。
- 未获得学校授权的生产教务系统直接写入。
- 使用真实学生数据训练公共模型。
- 允许模型直接执行数据库写操作或绕过权限读取数据。

## 4. 用户角色与权限

### 4.1 角色

- `system_admin`：配置组织、数据源、模型 Provider、质量规则和审计策略。
- `teacher`：管理本人课程、章节、任务，查看授权班级与学生，使用教师 AI 助手。
- `student`：查看本人课程、任务、计划、画像和问答记录，提交本人学习结果。
- `observer_teacher`：教师身份下查看指定学生详情；不能冒充学生执行写操作。
- `service_account`：供教务/LMS 数据同步使用，只能访问被授权接口和组织范围。

### 4.2 权限原则

- 身份、组织、课程、班级和学生范围均由服务端 Session/Token 解析，不能相信前端提交的角色。
- 教师只能访问本人教学关系内的数据；学生之间完全隔离。
- AI 调用沿用发起人的权限，模型不得扩大数据范围。
- 管理员能够配置模型，但默认不能查看学生问答正文；访问正文需要单独权限并写审计。

## 5. 功能需求

### FR-01 课程与章节中心

- 教师可以创建或维护课程基本信息、学期、教学班、章节和资源。
- 资源最少支持：文本、PDF 元数据、网页链接、现有视频链接和附件元数据。
- 资源必须存在 `draft / published / archived` 状态，学生只能看到已发布版本。
- 每次发布保留版本号、操作者、时间和内容摘要；旧版本可查看和回滚。
- 删除采用软删除，已产生学习记录的资源不得物理删除。
- 学生学习事件记录资源版本，避免资源更新后历史依据失真。

### FR-02 作业、练习与个人任务

- 支持客观题、简答题、阅读/观看任务和个性化练习。
- 教师可设置适用课程/班级/学生、开始时间、截止时间、预计时长和重试次数。
- 客观题由规则确定性判定；主观题支持教师反馈，AI 只能提供评分建议，不能在本轮直接确认正式成绩。
- 学生提交、评分、退回、完成和逾期均由服务端时间判定并持久化。
- 同一请求使用 `Idempotency-Key` 防止重复提交。
- 任务支持关联知识点、课程资源和个人计划，并能反向进入画像证据。

### FR-03 轻量课堂互动

- 教师可发起有时间窗口的签到、即时小测和“是否理解”反馈。
- 学生只能在当前教学班和有效时间窗口内参与。
- 页面实时显示已参与人数和总体分布；关闭活动后生成不可篡改的结果快照。
- 定位、人脸或摄像头监考不纳入本轮，避免额外隐私风险。

### FR-04 公告、待办与提醒

- 教师可以向课程或教学班发布公告，支持草稿、定时发布、撤回和已读统计。
- 发布、撤回必须使用页面内确认窗口，不使用浏览器原生弹窗。
- 学生首页汇总未读公告、待完成任务、逾期任务和计划提醒。
- 通知落库成功后才显示“已发布”；外部推送失败不得影响站内通知，但必须显示失败状态和重试入口。

### FR-05 学情分析与教学复盘

- 班级层：人数、参与率、任务完成率、成绩、知识点掌握、风险分布和趋势。
- 学生层：课程进度、提交记录、错题、掌握度、问答、个人计划、完成证据和风险原因。
- 每个数字必须携带 `source_version`、统计时间、数据范围和口径标识。
- 教师可从异常指标下钻到产生该指标的记录，不只显示结论。
- 报告在页面内直接查看和打印，不以“导出成功”代替实际内容展示。
- 统计任务失败时保留上一版并明确标记“旧版本”，不得用部分数据覆盖可信版本。

### FR-06 课程智能问答

- 智能问答必须由服务端调用 `course-ai-tutor` Skill；该 Skill 必须通过 `ModelGateway` 调用已启用的大模型生成答案，不能以关键词拼接或预设回答作为主要智能结果。
- Skill 负责问题理解、课程检索、上下文组装、模型调用、结构化输出和引用校验；业务接口负责身份、课程范围、持久化和审计。
- 支持新建会话、连续追问、引用课程资料、通用知识标识和转教师。
- 检索仅使用当前课程已发布且通过质量检查的资源版本。
- 回答至少返回：状态、正文、来源类型、引用、置信等级、模型、知识库版本、会话和轮次。
- 引用必须能定位到真实资源与片段；不存在的引用必须在返回学生前被拦截。
- 模型未配置或不可用时，只能展示课程检索结果和故障原因，明确标记“AI 未生成”；不得把离线规则或预设文本显示为大模型回答。
- 学生问题先完成敏感信息识别和最小化处理；原文与脱敏文本分别按权限保存。

### FR-07 教师 AI 助手

教师可在当前课程范围内发起：

- 根据章节资源生成教学摘要、知识点和课堂提问草案。
- 根据可信题库/资源生成练习草案和答案依据。
- 汇总班级薄弱知识点并解释证据。
- 将教学建议转为班级任务或个人任务草案。
- 对学生主观题给出反馈建议。

AI 结果默认是 `draft`。教师确认保存后，业务服务再次验证权限和字段，再写入正式业务表。模型不得直接发布公告、确认成绩或修改原始学习记录。

### FR-08 自动个性化学习计划

- 个性化学情由 `student-profile-analyzer` Skill 调用大模型生成，个性化计划由 `personalized-learning-planner` Skill 调用大模型生成，学习效果解释由 `learning-effect-evaluator` Skill 调用大模型生成。
- 三个 Skill 必须共享同一个已授权学情快照和证据清单，但分别使用独立的提示词、输出 Schema、版本号和运行记录。
- 成绩、掌握度、完成率、前后变化等数值由确定性统计服务计算；大模型只能解释、诊断和生成方案，不得发明或修改事实数值。
- 计划基于学生当前可信画像自动生成并生效，教师可查看、修改和恢复上一版本。
- 计划至少包含目标、知识点、任务、资源、难度、预计时间、截止时间、推荐原因和生成版本。
- 模型只生成结构化候选；计划服务必须完成 Schema、资源存在性、任务量、难度和时间边界校验。
- 数据质量达到阈值且候选通过规则校验时写为 `active_auto`；否则写为 `needs_review`，不能伪装为已生效。
- 教师修改后形成新版本并立即同步学生端，保留自动版本、教师版本和差异。
- 学生完成/逾期/反馈进入下一轮计算，但不得反向篡改历史计划。

### FR-09 知识库管理

- 课程知识库只接收已发布、已通过解析和质量校验的资源版本。
- 入库流程：解析 → 清洗 → 分段 → 去重 → 敏感信息检测 → 索引 → 抽样验证 → 激活。
- 新索引构建期间继续使用旧的 `active_index_version`；全部成功后通过原子切换激活。
- 支持按课程、资源、版本撤回并重建索引。
- 演示知识库、测试知识库和生产知识库使用不同命名空间及存储目录。

### FR-10 平台集成接口

- 提供课程、班级、用户、选课关系、资源、任务、成绩和学习事件的版本化 REST API。
- 支持全量初始化和基于游标/更新时间的增量同步。
- 外部对象使用 `(tenant_id, source_system, external_id)` 唯一映射，禁止只按姓名匹配学生。
- 同步服务只写入原始区/暂存区，不能直接修改可信业务表。
- 接口支持请求签名或 OAuth2 Client Credentials、限流、幂等、审计和重放防护。

### FR-11 可验证的个体学习处方引擎（核心差异化）

#### 11.1 处方组成

每一份处方必须是结构化业务对象，至少包含：

- `baseline_snapshot_id`：生成前的可信学情快照。
- `target_knowledge_points`：目标知识点及当前掌握度。
- `diagnosis`：问题、原因、证据和置信等级。
- `intervention_items`：资源、练习、问答、复习方法、难度和预计时长。
- `expected_outcome`：预计改善指标、目标值和评估窗口。
- `stop_or_adjust_rules`：达到、无效、过难或数据不足时如何调整。
- `plan_version`、生成模型/规则版本和教师修改记录。

#### 11.2 个体差异要求

- 不能仅按“优秀/中等/待关注”三个分组复制统一任务。
- 即使两个学生总分相同，也应根据错题类型、知识点、完成习惯、问答和近期趋势生成不同处方。
- 处方推荐必须优先使用当前课程已发布资源；不存在合适资源时明确标记缺口，不伪造资源。
- 单日总时长、任务数量和难度必须受规则约束，避免模型生成不合理任务量。

#### 11.3 效果验证

- 处方开始时冻结基线快照，结束时生成同口径结果快照。
- 效果至少比较：目标知识点掌握度、相关题正确率、任务完成率和求助情况。
- 页面区分“观察到改善”“未观察到改善”“数据不足”，不得把自然波动直接宣传为 AI 导致的提升。
- 展示实际变化、目标差距和可用样本数量；没有足够数据时不给出确定性结论。
- 历史基线、处方、执行事件和结果快照不可被新一轮覆盖。

#### 11.4 下一轮自动调整

- 达标：降低重复训练比例，进入迁移或拓展任务。
- 部分改善：保留有效任务，调整薄弱环节的解释方式或难度。
- 无改善：更换资源、方法或任务类型，并提示教师关注。
- 明显退步或连续逾期：降低负荷并进入教师复核，不自动堆叠任务。
- 调整结果形成新版本；学生和教师均能看到“与上一轮相比改变了什么”。

#### 11.5 教师控制与真实性

- 符合质量阈值的处方可自动生效，教师可以查看、修改、暂停或恢复。
- 教师修改必须保留原自动版本和修改原因，不能覆盖生成证据。
- 模型只生成候选，资源存在性、时间、权限、质量和任务量由确定性服务校验。
- 只有处方、任务和评估窗口全部落库成功后，页面才显示“处方已生效”。
- 任何模型故障、数据版本变化或保存失败都必须显示真实状态并提供重试。

#### 11.6 竞争性成果展示

教师端为每名学生提供一张“处方效果卡”，固定显示：

- 本轮核心问题及三条以内的关键证据。
- 已采取的个体干预和完成情况。
- 基线值、目标值、当前值和评估截止时间。
- 本轮判断及可信度/数据充分性。
- 下一轮保留、删除或调整的内容及原因。

班级端只聚合处方覆盖率、执行率、改善率、数据不足率和教师修改率，并支持下钻到原始证据。不得只显示一个没有计算口径的“AI 提升百分比”。

### FR-12 前端 API Key 配置

#### 12.1 前端入口

教师/管理员端新增“**AI 接口**”入口。普通学生不显示配置入口，只显示当前问答是否处于 AI 可用、AI 故障或 AI 未配置状态。

前端配置区只展示：

- 一个 `API Key` 密码输入框。
- 一个“保存并验证”按钮。
- 验证结果：AI 可用、验证失败或尚未配置。
- 失败原因和重新输入入口。

前端不提供 Provider、API 地址、模型名称、向量模型、重排模型、用途绑定或高级参数选择。上述内容全部使用服务端预设配置，避免普通使用者误配。

#### 12.2 前端配置流程

```text
管理员打开 AI 接口
  → 输入 API Key
  → 点击“保存并验证”
  → 服务端使用预设 Provider、地址和模型执行最小化测试
  → 验证成功后保存密钥引用并启用 AI
```

- API Key 可在前端输入，但只能通过受保护请求一次性提交给服务端；不得写入 localStorage、IndexedDB、前端配置文件或普通日志。
- 服务端保存到受保护的本地密钥存储或部署环境密钥中，数据库只保存 `secret_ref` 和密钥后四位用于识别。
- 编辑页面留空表示不修改原密钥；更换密钥需要重新输入并重新测试。
- 非管理员不能查看或修改 API Key。
- Provider、API 地址、模型和 Skill 绑定由服务端配置文件或发布版本固定，不在前端显示或修改。

#### 12.3 强制 Skill 编排

| 业务能力 | 必须调用的 Skill | 大模型职责 | 确定性服务职责 |
|---|---|---|---|
| 智能问答 | `course-ai-tutor` | 理解问题、组织答案、连续追问 | 鉴权、检索范围、引用校验、落库 |
| 个性化学情 | `student-profile-analyzer` | 解释优势、薄弱点、可能原因和学习特点 | 计算成绩、掌握度、趋势和证据列表 |
| 个性化计划 | `personalized-learning-planner` | 生成目标、任务组合、难度和推荐原因 | 资源存在性、负荷、期限、权限、版本校验 |
| 效果评估 | `learning-effect-evaluator` | 解释效果并生成下一轮调整建议 | 计算基线、结果、变化值和数据充分性 |

- 前端不得直接请求第三方模型 API，所有调用必须通过服务端 Skill 编排。
- Skill 不得绕过 `ModelGateway` 直接读取 API Key 或调用供应商 SDK。
- 没有成功的 `ai_run_id`、Skill 版本和模型响应记录时，页面不得标注“AI 智能生成”。

## 6. 大模型 API 接入需求

### 6.1 设计原则

- Provider 可替换：兼容国内可访问的 OpenAI-compatible API，也支持学校私有模型网关。
- 智能问答、个性化学情、个人计划和效果评估必须由对应 Skill 经 ModelGateway 调用大模型；规则实现不能伪装成模型生成。
- 浏览器只在管理员主动录入时短暂持有密钥并立即提交；服务端永不向浏览器回传密钥，前端不得持久化。密钥最终仅存在于服务端受保护的密钥存储中。
- 聊天、向量、重排能力分别声明，不能假设一个 Provider 全部具备。
- 业务层不得直接调用供应商 SDK，统一经过 `ModelGateway`。
- 模型响应是不可信输入，必须校验、脱敏、限长和记录版本。
- 默认不允许服务商使用输入输出训练模型；配置页必须记录数据留存和训练策略。

### 6.2 Provider 配置

建议服务端配置项：

| 配置 | 说明 |
|---|---|
| `provider_id` | 内部稳定标识 |
| `api_base_url` | HTTPS API 地址，限制允许的域名/IP |
| `secret_ref` | 密钥引用，不保存明文密钥 |
| `chat_model` | 对话模型 |
| `embedding_model` | 向量模型，可选 |
| `rerank_model` | 重排模型，可选 |
| `timeout_ms` | 调用超时 |
| `max_retries` | 仅对安全可重试错误生效 |
| `data_region` | 数据处理地区 |
| `retention_policy` | 服务商留存策略 |
| `training_opt_out` | 是否明确关闭训练使用 |
| `enabled_capabilities` | chat、embedding、rerank、vision 等 |

前端管理页允许管理员填写 `api_key`，但只能一次性提交到服务端密钥写入接口。服务端响应只返回 `secret_ref`、掩码和测试状态，不返回原始密钥；前端不得将密钥保存到 localStorage、IndexedDB 或静态配置文件。

### 6.3 ModelGateway 内部契约

```ts
interface ModelGateway {
  healthCheck(providerId: string): Promise<ProviderHealth>;
  chat(request: ChatRequest): Promise<ChatResult>;
  embed(request: EmbeddingRequest): Promise<EmbeddingResult>;
  rerank(request: RerankRequest): Promise<RerankResult>;
}
```

`ChatRequest` 至少包含：

- `request_id`、`purpose`、`actor_id`、`tenant_id`。
- `course_id`、`session_id` 和由服务端生成的授权范围。
- system 指令版本、脱敏后的消息、证据片段、结构化输出 Schema。
- 最大 Token、温度、超时和安全策略。

`ChatResult` 至少包含：

- `provider_id`、`model`、`model_revision`。
- `output_text` 或结构化 `output`。
- `finish_reason`、Token 使用量、耗时。
- `safety_flags`、`provider_request_id` 和错误分类。

### 6.4 应用 API 草案

所有接口统一使用 `/api/v1`，返回 `requestId`，写接口要求 CSRF 或服务账号签名。

| 方法 | 接口 | 权限与用途 |
|---|---|---|
| GET | `/api/v1/admin/ai/status` | 管理员查看是否已经配置及可用状态，不返回密钥、地址或模型详情 |
| PUT | `/api/v1/admin/ai/key` | 一次性写入或替换 API Key，并使用服务端预设模型完成验证 |
| POST | `/api/v1/ai/qa/sessions` | 学生创建当前课程问答会话 |
| POST | `/api/v1/ai/qa/sessions/:id/messages` | 提问或追问；服务端绑定学生和课程范围 |
| POST | `/api/v1/ai/qa/messages/:id/feedback` | 有帮助、未解决、举报引用错误 |
| POST | `/api/v1/ai/teacher/drafts` | 教师生成摘要、题目、反馈或任务草案 |
| POST | `/api/v1/ai/plans/:studentId/generate` | 生成个人计划候选并由计划服务校验/版本化 |
| GET | `/api/v1/ai/runs/:runId` | 查询运行状态、来源、错误和是否已保存 |
| POST | `/api/v1/knowledge/courses/:courseId/reindex` | 教师/管理员触发课程知识库重建 |
| GET | `/api/v1/knowledge/courses/:courseId/status` | 查看解析、隔离、索引和激活版本 |

建议统一成功响应：

```json
{
  "success": true,
  "requestId": "req_xxx",
  "data": {},
  "meta": {
    "sourceVersion": "v_xxx",
    "modelRunId": "airun_xxx",
    "persisted": true
  }
}
```

统一失败响应必须说明：发生了什么、是否保存、是否可重试、重试入口。例如：

```json
{
  "success": false,
  "requestId": "req_xxx",
  "error": {
    "code": "AI_PROVIDER_TIMEOUT",
    "message": "模型服务超时，本次问题已保存但尚未生成回答。",
    "saved": true,
    "retryable": true
  }
}
```

### 6.5 调用状态机

```text
received → redacted → retrieving → generating → validating
         → completed_persisted
         → degraded_offline
         → failed_retryable / failed_terminal
```

只有 `completed_persisted` 才能在页面显示“生成并保存成功”。模型返回成功但数据库写入失败时，整体状态必须为失败。

## 7. 防止脏数据污染的数据治理需求

### 7.1 五层数据区

```text
外部数据/文件/API
  → Raw 原始区（不可改，只保存来源与摘要）
  → Staging 暂存区（字段映射、格式校验、去重）
  → Quarantine 隔离区（错误、冲突、可疑记录）
  → Curated 可信区（通过规则并经批次确认）
  → Serving 服务区（画像、统计、检索索引和计划快照）
```

- AI 和页面统计只能读取 `Curated/Serving`，不得读取未确认的 Raw/Staging。
- 隔离记录不参与班级平均分、画像、风险、个性化计划或知识库索引。
- 每次处理保留 `batch_id`、来源、文件摘要、规则版本、操作者、时间和父版本。

### 7.2 演示、测试与正式数据隔离

- `environment = demo / test / production` 必须进入主键或命名空间边界。
- 合成数据必须标记 `synthetic = true`，生产统计默认排除。
- 演示数据库、测试数据库和正式数据库使用不同目录/实例；不得靠页面筛选实现隔离。
- 发布 ZIP 不包含用户 runtime、模型密钥、真实日志或生产索引。
- 禁止将演示账号、匿名编号与真实学生记录自动合并。

### 7.3 身份匹配和去重

- 学生匹配使用稳定外部标识和组织范围，不按姓名、手机号后四位等模糊字段自动合并。
- 出现一对多、多对一或课程关系冲突时进入 Quarantine，由管理员处理。
- 每条学习事件使用 `source_event_id` 或内容指纹幂等；重复同步不能重复计分。
- 迟到事件允许重算新版本，但不能修改已发布的历史快照。

### 7.4 字段质量规则

至少校验：

- 必填、类型、枚举和时间格式。
- 分数范围、完成时间不得早于开始时间。
- 课程、教学班、学生和任务的引用完整性。
- 未来时间、异常时长、重复提交和不合理突变。
- 列名自动匹配只生成映射建议，置信度不足时要求确认。
- 关键字段冲突不采用“最后写入覆盖”，必须进入隔离或按已确认的来源优先级处理。

### 7.5 来源优先级与冲突

建议默认顺序：

1. 经授权教务/教学平台正式 API。
2. 教师在系统内产生并确认的业务记录。
3. 管理员确认的补录批次。
4. 演示合成数据。
5. AI 推断结果。

AI 输出永远不能覆盖 1～3 级事实数据。推断内容单独保存，字段带 `inferred = true`、模型版本、依据和置信度。

### 7.6 批次激活与回滚

- 导入批次通过校验后仍处于 `validated`，完成确认和事务写入后才成为 `active`。
- 统计和画像使用明确的 `active_data_version`，不能查询“最新几条记录”拼成不一致结果。
- 激活失败全部回滚，继续使用上一可信版本。
- 管理员可以停用某批次并重新生成服务快照，操作需审计。

### 7.7 AI 上下文防污染

- 只允许当前课程激活资源进入 RAG；草稿、撤回、隔离和其他课程内容不得进入。
- 课程资源中的文本视为数据，不得执行其中包含的提示词或指令。
- 用户上传内容经过 Prompt Injection、脚本、隐藏文本和敏感信息检查。
- 会话按租户、课程、学生和 session 隔离，切换课程不得复用历史证据。
- 模型生成内容不能自动写回知识库；必须经过教师确认、资源化和新一轮索引流程。
- 问答反馈可用于质量评估，但默认不得直接改变正式答案或训练模型。

## 8. 数据模型增量草案

建议新增或规范以下实体，最终名称可在设计阶段调整：

- `data_sources`、`ingestion_batches`、`raw_records`、`quarantine_records`。
- `identity_mappings`、`data_quality_results`、`data_versions`。
- `course_sections`、`course_resources`、`resource_versions`。
- `assessments`、`assessment_items`、`submissions`、`grading_events`。
- `classroom_activities`、`activity_responses`、`announcements`、`notifications`。
- `knowledge_indexes`、`knowledge_chunks`、`index_versions`。
- `ai_providers`、`ai_policies`、`ai_runs`、`ai_evidence`、`ai_feedback`。
- `personal_plan_versions`、`personal_plan_items`、`plan_execution_events`。

原则：原始事实、业务状态、派生指标和 AI 推断不得混在同一字段中相互覆盖。

## 9. 非功能要求

### 9.1 安全

- API 全部服务端鉴权；对象级权限防止 IDOR。
- 模型 Base URL 使用允许列表，防止 SSRF；禁止访问 localhost、元数据地址和内网未授权地址。
- 密钥、Session、CSRF、原始密码和完整敏感数据不得进入模型提示词或日志。
- 对外 API 限流、请求大小限制、超时、审计和失败熔断。

### 9.2 可用性

- AI 超时不影响课程、任务和画像等非 AI 基础功能。
- 服务重启后 AI 运行、问答、任务和计划状态可从 SQLite 恢复。
- 用户可看见处理状态，不显示无限加载。
- 所有错误同时说明“发生了什么、数据是否保存、下一步怎么做”。

### 9.3 性能

- 普通业务接口 P95 目标小于 1 秒；班级聚合 P95 目标小于 2 秒。
- AI 首个状态反馈小于 1 秒；模型完整回答目标可配置超时 30～60 秒。
- 长耗时索引和统计采用任务状态查询，不阻塞 HTTP 连接。

### 9.4 可观察性

- 记录 requestId、actor、purpose、provider、model、耗时、Token、数据版本和结果状态。
- 不记录模型密钥和不必要的原始敏感正文。
- 提供 Provider 可用率、超时率、降级率、引用拦截率和保存失败率。

## 10. 验收标准

### AC-01 基础教学闭环

- 教师创建章节、发布资源、创建任务；学生查看并提交；教师看到真实提交和统计。
- 刷新、返回和服务重启后状态不丢失。
- 未落库的操作不得显示成功。

### AC-02 数据隔离与防污染

- 导入包含重复学生、非法分数、错课程和未来时间的批次，错误记录进入隔离且不改变现有班级统计。
- 同一事件重复同步 3 次只产生一条有效业务记录。
- demo/test/production 数据互不可见；生产接口默认不返回 synthetic 数据。
- 批次激活失败后，页面仍使用上一可信版本并显示版本时间。

### AC-03 大模型 Provider

- 至少通过一个国内可访问的 OpenAI-compatible Provider 完成健康检查、对话和结构化输出。
- 管理员能够在前端输入 API Key 并完成保存验证；Provider、地址、模型和 Skill 绑定使用服务端预设值。
- 切换 Provider 不需要修改问答、计划和教师助手业务代码。
- 密钥不出现在前端源码、网络响应、Git、日志和发布包。
- 模型超时后问题仍保存，可重试并且不会重复产生记录。

### AC-04 课程问答

- 不少于 100 条测试集，覆盖同义改写、错别字、多轮追问、计算、无资料、跨课程、提示注入和越权问题。
- 课程引用全部可定位到当前课程激活资源；伪造引用被拦截。
- 未配置模型时明确显示“AI 未生成”；允许单独展示离线检索结果，但不得将其标注为 AI 回答。
- 学生 A 的会话、画像和证据不会进入学生 B 的回答。
- 每条标注“AI 生成”的答案均存在对应 `course-ai-tutor` Skill 运行记录、模型调用记录和成功持久化记录。

### AC-05 教师助手与个性化

- AI 生成的题目、反馈和任务先成为草案，确认后才进入业务表。
- 选择 3 名学情不同学生，计划的目标、任务、难度或资源至少有两项实质差异。
- 数据质量不足时计划显示 `needs_review`，不得显示自动生效成功。
- 教师修改计划后形成新版本，学生端同步，旧版本和依据仍可追溯。
- 每份标注“AI 学情”的画像存在 `student-profile-analyzer` Skill 和真实模型调用记录；每份 AI 计划存在 `personalized-learning-planner` Skill 和真实模型调用记录。
- 禁用 Provider 后重新生成学情时必须明确失败或等待配置，不能返回原规则模板并标注为 AI 生成。

### AC-06 安全与权限

- 修改 URL、courseId、studentId 或 sessionId 无法越权。
- 教师观察视角不能代替学生提交任务或提问。
- 模型不能调用未授权工具，也不能根据资源正文中的恶意指令读取其他课程数据。

### AC-07 核心差异化能力验收

- 使用不少于 30 名合成学生、至少 3 类不同薄弱原因完成端到端处方测试。
- 任取 5 名学情不同学生，其处方在目标知识点、任务、难度、资源或调整规则中至少有两项实质差异。
- 任取 2 名总分接近但错因不同的学生，系统不得生成完全相同的处方。
- 每份处方均可追溯到有效数据版本和具体证据，撤回或隔离的数据不能继续作为依据。
- 模拟达标、部分改善、无改善、退步和数据不足五种结果，系统分别给出符合规则的下一轮动作。
- 数据不足时必须显示“无法判断”，不得生成虚假改善率。
- 教师修改、学生执行、结果评估和下一轮调整在服务重启后仍可恢复。
- 自动化测试能够证明生成、落库、执行、评估、调整不是前端静态演示。

## 11. 建议实施顺序

### P0：可信数据与模型底座

1. 数据五区、版本、隔离、幂等、来源追踪。
2. `/api/v1` 约定、统一错误和真实持久化状态。
3. ModelGateway、Provider 配置、密钥管理、健康检查。
4. 前端 API Key 输入与保存验证。
5. 课程知识库版本与 AI 运行审计。

### P1：最小教学闭环

1. 课程章节与资源版本。
2. 作业/练习/个人任务及提交反馈。
3. 公告、待办、逾期提醒。
4. 统一班级/学生数据和来源口径。

### P2：AI 与个性化闭环

1. 课程智能问答和多轮追问。
2. 教师 AI 助手草案。
3. 可验证的个体学习处方、教师调整和执行反馈。
4. 基线/结果同口径对比、效果判断和下一轮自动调整。

### P3：课堂与外部集成

1. 轻量签到、即时小测和课堂反馈。
2. 教务/LMS 增量同步 API。
3. 可选站外消息适配器。

## 12. 风险与决策点

实施前需要确认以下决策：

1. **产品路线**：采用“教学干预引擎”路线，并将“可验证的个体学习处方”作为唯一核心差异化功能，不建设完整 MOOC/直播平台。
2. **模型范围**：首期接入一个国内可访问的 OpenAI-compatible 服务，同时保留私有模型适配能力。
3. **模型配置**：管理员前端只输入 API Key；Provider、API 地址、模型和 Skill 绑定由服务端预设，密钥一次性提交到服务端密钥存储且不回显。
4. **AI 写入策略**：问答可直接展示；教师内容默认草案；个人计划通过规则校验后可自动生效。
5. **真实数据接入**：首期先完成标准 API 和隔离流程，不在未获得授权时接入真实学生数据。
