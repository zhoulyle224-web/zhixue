# 智学双擎 M2.5 修改与验收报告

日期：2026-09-17  
依据：`REQ-M2.5_M2到M3衔接约束与最小补强需求_20260917.md`  
范围：仅本地项目工作副本的 M2 来源契约、迁移、教师页面适配与自动化测试。未实施 M3 业务。

## 已实现

1. 批次模式 `POST /api/analyze` 每次成功都新建一条分析运行，返回顶层 `analysisRunId`、`batchId`、`status: "completed"`。旧的直接分数模式保持原响应行为。
2. 研判结果的 `_evidence` 随结果写入运行时 SQLite，至少包含 `analysisRunId`、`batchId`、`context`、`fileHash`、`validRows`、`studentCount`、`skillId`、`skillVersion`、`analyzedAt`。保留 M2 原有证据字段以兼容现有页面。
3. 新增 `GET /api/analysis/:analysisRunId?context=teacher:<课程>:<班级>`，按固定 ID 返回 `{analysisRunId,batchId,context,status,result,_evidence}`。不存在返回 404 `ANALYSIS_NOT_FOUND`，上下文不匹配返回 403 `ANALYSIS_CONTEXT_MISMATCH`，非完成研判或非确认批次返回 409 `ANALYSIS_NOT_COMPLETED`。
4. 批次的事实状态在研判后保持 `confirmed`。重复确认返回原 `confirmedAt` 和 `alreadyConfirmed: true`，不重复写批次或有效记录；重复研判创建新运行，不覆盖旧运行。
5. `/api/import/latest` 标记 `usage: "page_restore_only"`，只返回最新批次的已完成研判，且该批次须已确认。它用于页面恢复，不是 M3 的固定来源引用。
6. 教师端证据区显示研判 ID，切换班级或开始新导入时清除旧 ID；页面根据研判记录显示“研判完成”，不再把批次改为 `analyzed`。
7. 兼容旧 M2 SQLite：启动时只补充分析运行 `status` 列，并把已有、具有 `confirmed_at` 的 `analyzed` 批次规范为 `confirmed`；不删表、不清记录。旧分析 ID 保持原值，可按 ID 查询。

## 接口与下游约束

批次模式的最小调用顺序：

```text
POST /api/import/validate
→ POST /api/import/:batchId/confirm
→ POST /api/analyze { "context": "teacher:7:1", "batchId": "b_..." }
→ GET /api/analysis/:analysisRunId?context=teacher%3A7%3A1
```

M3 后续只能消费符合以下全部条件的固定快照：`batch.status === "confirmed"`、`analysis.status === "completed"`、分析与批次的 `context` 和 `batchId` 一致。任务草案需记录 `sourceAnalysisRunId` 和 `sourceBatchId`，不能记录 `source=latest`，不能重新计算 M2 事实或修改历史研判。此处是给 M3 的契约，**本次没有实现任务创建/发布/反馈**。

`context` 目前只是本地业务隔离参数，尚无 M4 服务端登录授权；调用者若自行伪造其他班级的 context，现阶段无法作为真实身份安全边界。因此接口不应暴露给真实学生数据或声称已具备生产权限控制。
